## 1. 项目理解与架构判断

当前是有部分纯逻辑实现的脚手架。API、Worker、图节点中的 `TODO(impl)` 和尚未生成的迁移属于预期开发任务。已注册 33 个 OpenAPI 路径不代表 33 个接口已实现。

项目目标是 AI 分镜生产的调度、质量控制和成本审计。主要成果应是图像层的角色一致性、自动质检、受控重试和真实对照实验；视频只承担少量端到端验证。总预算 200 元，计划周期约两周。不训练模型，不扩展成完整剪辑平台或多租户产品。

现有技术路线合理，可以保留：FastAPI 提供 API/SSE，LangGraph 决定流程转移，ARQ 执行后台任务，MySQL 保存持久状态与账目，Redis 承担队列和临时协调，本地文件保存素材，FFmpeg 合成。避免让图节点与 Worker 分别维护一套重试和恢复状态。

必须落实的约束：

- A 角色确认、B 分镜审核、C 合规终审都是强制人工关卡；审核绑定具体运行和素材版本。
- 五维质检由本地规则判定，阈值 0.4；置信度低于 0.6 转人工；合规 `blocked` 禁止自动重试。
- 锚定包含稳定的角色特征、参考图、同场景已接受帧；多人同框必须能追溯每个角色的版本。
- 所有付费调用经过 Provider，失败也留痕；重试有上限，暂停保留成功产物，恢复不能重复付费。
- 数据库、HTTP 和运行中的子进程操作遵守异步约束；费用以整数分记录。
- 保留约 100 张盲抽对照和 50—100 张人工标注黄金集。模型、参数、提示词和样本划分可追溯；指标和节省金额必须来自实测。

## 4. 正式编码前应统一的契约

以下是对照现有文档与代码发现的具体问题。此次仅记录，不修改业务行为；后续应先修订相应契约，再补有针对性的测试。

| 优先级 | 问题与影响 | 建议落实方式 |
| --- | --- | --- |
| P0 | `providers/base.py` 先调供应商、后扣账，并发调用可以先产生超过预算的实际费用；`cost_service.py` 多级账本失败可能保留前一级扣费 | 先在同一事务预留项目/类别/镜头额度，再调用；以真实账单结算或释放，超时未知状态不能直接退回额度后重发 |
| P0 | 幂等命中返回失败结果，路由可能继续降级；超时后重试无法判断远端是否已接受 | 持久保存请求状态、供应商任务 ID 和最终结果；重放返回已有结果；不确定状态先查询与对账 |
| P0 | 供应商信号量 TTL 为 60 秒，视频超时为 600 秒，缺少持有者标识与续租 | 使用带所有者的租约和续期；只释放自己持有的锁，并测试超时与进程退出 |
| P0 | 质检缺失或非法分数会转成 0，可能被当作合格；现有测试不能证明这是合理行为 | 完整验证五维字段、有限数值和范围；解析失败按约定重试或转人工，不默认通过 |
| P0 | 缺少 B 关卡放行接口；审核请求缺少运行/候选素材/版本等定位；启动 run 又要求角色已确认，与图中先提取角色冲突 | 先统一状态迁移及 API；审核引用具体 run、attempt 和版本，拒绝过期审批；明确首次运行从何处进入 |
| P1 | Provider 仅按供应商名索引，同一家图像和视频实现会冲突；视觉 `judge()` 缺少统一记账上下文 | 按能力与供应商共同定位，视觉/LLM 也沿用相同的预算、追踪和计费路径 |
| P1 | 调用与抽卡追踪不足以区分运行、实验组和多人角色版本 | 迁移生成前补齐 run、实验配置/组别和角色版本快照；重跑不污染原实验数据 |
| P1 | 图像审核写 `locked_attempt_id`，视频合成又用它找视频片段 | 明确图像/视频两类被接受产物；生成可按场景集中，最终合成仍按叙事顺序 |
| P1 | SSE 用 `BLPOP`，多个页面会分走事件；Redis socket 超时 5 秒小于阻塞等待 15 秒 | 明确广播与重连补发语义，选用能满足要求的 Redis 机制，统一超时并测双客户端 |
| P1 | `/budget/config` 排在 `/{project_id}` 后，被动态路由匹配 | 将静态路由前置并验证实际 HTTP 路由命中 |
| P1 | docs/03 的混淆矩阵标签与召回率公式不一致 | 统一正类后更新表格、公式、脚本与报告；建议以“缺陷”为正类，漏放=FN，误杀=FP |
| P1 | 单价、免费额度和成本比例不一致且尚未验证账户条件 | 首次真实调用前核对供应商接口、模型 ID、账户额度和价格；预计节省与实际支出分开报告 |
| P2 | `start.ps1` 用当前 PowerShell 会话的后台 Job；`stop.ps1` 含只读 `$PID` 赋值及按端口杀进程逻辑 | 当前使用下文两个前台终端命令；后续修复脚本时按项目进程身份管理启停 |
| P2 | Dockerfile 把后端放到 `/app/backend`，启动目录仍为 `/app`；缺少可运行镜像的实测 | 部署阶段统一工作目录/导入路径，并实际构建、启动镜像；本机测试不能代替发布验收 |

建议评估口径：以缺陷为正类，TP=机器拦截且人工判坏，TN=机器放行且人工判好，FN=机器放行但人工判坏，FP=机器拦截但人工判好。缺陷召回率=TP/(TP+FN)，误杀率=FP/(FP+TN)。人工待审结果单列，不能偷偷算作通过。校准样本与最终评估样本分开，避免在同一批图上调阈值又汇报效果。

docs/08 对“已实现模块不改行为”的要求，应以其预期保障为目标保留。上表涉及实际矛盾，不能仅因被标记为“完整”就跳过验证。39 项通过也不应被解读为整条基础设施已验证。

## 5. 开发命令与实施顺序

在项目根目录启动基础设施：

```powershell
docker compose --env-file backend/.env -f deploy/compose.dev.yml up -d --wait
docker compose --env-file backend/.env -f deploy/compose.dev.yml ps
```

在两个独立终端分别运行 API 与 Worker；各自用 Ctrl+C 退出：

```powershell
Set-Location G:\storyboard-pipeline\backend
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8100 --reload
```

```powershell
Set-Location G:\storyboard-pipeline\backend
.\.venv\Scripts\python.exe -m arq app.workers.arq_settings.WorkerSettings
```

Swagger：`http://127.0.0.1:8100/docs`；健康检查：`http://127.0.0.1:8100/api/v1/health`。健康检查必须核对 JSON 中各依赖结果，不能只看 HTTP 200。

停止项目基础设施并保留数据：

```powershell
docker compose --env-file backend/.env -f deploy/compose.dev.yml stop
```

重建相同 Windows/Python 3.13 依赖环境时：

```powershell
Set-Location G:\storyboard-pipeline\backend
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt -c constraints-win-py313.txt
```

推荐第一批实现：先统一上表 P0 契约与必要字段，解决现有静态检查问题，再生成并人工核对初始迁移，完成项目/角色 CRUD 和一个有预算、幂等保障的图像调用。随后接质检闭环、真实对照数据、完整运行与审核恢复，最后接少量视频和部署。

每一批要求测试、Ruff、mypy 通过；涉及数据库验证迁移一致性；涉及恢复/预算/审核必须验证对应失败场景；真实模型测试先检查账户额度并严格计费。当前没有生成首个迁移，没有实现业务占位函数，也没有发起付费模型调用。
